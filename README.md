# Tripdeep

Tripdeep is a local-first multi-agent travel planning workspace. The agent prompts in `Agent_prompt/` and the Document-agent notes at the repository root are the functional source of truth. The source review and input/output matrix live in [structure/AGENT_INVENTORY.md](structure/AGENT_INVENTORY.md); the system decisions and boundaries are in [structure/ARCHITECTURE.md](structure/ARCHITECTURE.md).

## Technologies and Tools

- **Frontend:** React 19, TypeScript 6, Vite 8, React Router 7, and Lucide icons.
- **Backend:** Python 3.14, FastAPI, Uvicorn, Pydantic Settings, and HTTPX.
- **Database:** PostgreSQL 18 with psycopg 3's async pool and JSONB document storage. MongoDB and process-local memory adapters are also available for compatibility and tests.
- **Live public data:** Open-Meteo geocoding and forecasts; OpenStreetMap via Overpass and Nominatim for nearby place listings.
- **Production identity/storage:** Supabase Auth and PostgreSQL, with a private Supabase Storage bucket for trip documents.
- **Production hosting recommendation:** Cloudflare Pages for the React frontend (`*.pages.dev`) and a Render web service for FastAPI. Render's free service can sleep when idle; Supabase free resources have quota/availability limits. This is a no-cost starter deployment, not an uptime or backup guarantee.
- **Quality checks:** pytest, TypeScript/Vite production build, and ESLint.
- **Local development:** VS Code, PowerShell, Node/npm, and the PostgreSQL Windows service. Docker is not required.

**LLM status:** The orchestrator, Validator, finance, insurance and document checks are deterministic by design; they do not use a generative model to make authoritative decisions. Clothing suggestions may use the optional local Ollama model. The recommended cloud alternative is Cloudflare Workers AI's Llama 3.1 8B Instruct model when its free allowance is available. Cloud AI is off unless configured and enabled by the user for an individual trip. Only coarse weather availability, baseline clothing suggestions and generic activity types are sent; destinations, exact travel dates, activity names, account details and uploaded files are excluded. Forecasts, costs and policy facts are never generated by the model. Free-tier quotas and provider terms can change.

To enable the local model after installing Ollama and downloading a model:

```powershell
ollama pull qwen2.5:3b
```

For local Ollama, set these entries in `.env`, then restart the backend:

```text
LLM_PROVIDER=ollama
OLLAMA_BASE_URL=http://127.0.0.1:11434
OLLAMA_MODEL=qwen2.5:3b
```

The model only adds styling notes; if it is unavailable or returns invalid output, the planner reports that and keeps the deterministic, forecast-based clothing suggestions.

For optional cloud styling, set `LLM_PROVIDER=cloudflare_workers_ai`, `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, and (optionally) `CLOUDFLARE_AI_MODEL` on the backend only. Users must enable the per-trip cloud-AI checkbox before any prompt is sent. Never expose the Cloudflare API token to Vite or commit it to Git.

## Current Implementation

- React, Vite and TypeScript workspace centered on trip inputs, saved trips, and a consolidated plan.
- FastAPI API with the 12-agent registry, trip persistence, execution auditing and internal Validator checks.
- PostgreSQL persistence through psycopg's async connection pool, using JSONB records and startup-created indexes.
- One trip-planning submission runs the orchestrator and relevant specialists; the user sees one consolidated plan rather than agent controls or QA output.
- Destination lookup and date-bounded weather forecasts use Open-Meteo. Named accommodation and attraction suggestions use OpenStreetMap public APIs.
- Weather results are shown for every selected date. Dates outside Open-Meteo's forecast window are explicitly marked unavailable; no weather is invented.
- The itinerary distributes sourced place listings across the selected trip dates. Clothing suggestions use each day's available weather and scheduled places; out-of-window outfits are marked as general guidance.
- The final plan includes a document checklist, trip-linked uploads, possible insurance-policy attachments and finance results. Upload documents from **Travel documents** and link them to the trip; filenames only suggest document type, and policy terms and coverage must be confirmed with the insurer.
- Finance totals include provider-confirmed amounts only. Since booking and insurance providers are not configured, the plan states when no verified prices or policy comparisons are available rather than inventing them.
- Map listings do not claim room availability, independently verified star classification, or prices. Live transport booking, hotel rates, insurance offers, and confirmed Jain menus require their own authorized providers.
- Deterministic Validator checks for required fields, date ordering, traveler/room arithmetic, document expiry, cross-agent conflicts and unavailable/unverified output.
- Automatic reproduction records on execution exceptions; sanitized payloads redact credential-like fields. Reproduction replay is available for stored cases.
- Bounded exponential retry and circuit-breaker utilities for provider adapters.
- Agent implementations return local deterministic advice where justified, and explicit unavailable/needs-input outcomes when live providers or evidence are missing.

Hotel, transport, weather, tour-guide and insurer live inventory is not enabled until authorized provider integrations and credentials are configured. No hotel, flight, weather, policy, price or offer data is fabricated. The dietitian correctly returns `needs_input` when child ages or allergy confirmation are absent, and otherwise remains degraded until a verified Jain-food context is available.

### Agent/provider selection

| Agent responsibility | Selected no-cost source or method | LLM use |
| --- | --- | --- |
| Trip planner/orchestrator | Local deterministic routing | None; it selects and coordinates specialists. |
| Validator/QA | Local deterministic rules | None; validation must be reproducible. |
| Destination and weather | Open-Meteo public geocoding/forecast API | None; show provider values and forecast limits. |
| Hotels and attractions | OpenStreetMap through Overpass; Nominatim is a bounded fallback | None; map listings are not availability or booking offers. |
| Documents | Local text/CSV/JSON extraction; private object storage in production | None; policy/passport contents are not sent to a model. PDF/image OCR is not configured. |
| Insurance | User-linked policy filename hints; manual insurer confirmation | None; there is no configured free, authoritative insurer quote/coverage API. |
| Finance | Local arithmetic over provider-confirmed line items only | None; unknown prices stay unknown. |
| Clothing stylist | Deterministic forecast-based rules | Optional Ollama locally or opt-in Cloudflare Workers AI with minimized prompt data. |
| Transport | Explicitly unavailable until a legitimate booking provider is configured | None; no live free booking/availability API is configured. |
| Health and dietitian | General non-diagnostic guidance and input checks | None; no personalized medical conclusions or unverified menu claims. |

Open-Meteo's free API is rate-limited and intended for non-commercial use; attribute Open-Meteo and confirm its current terms before any commercial use. OpenStreetMap public endpoints have usage policies and no uptime guarantee. If public traffic reaches their limits, use a suitable licensed provider rather than rotating endpoints or overstating freshness.

## Run With Docker Compose

Requirements: Docker Desktop with Compose.

```powershell
Copy-Item .env.example .env
docker compose up --build
```

The frontend is at `http://localhost:5173`, the API at `http://localhost:8000`, and OpenAPI docs at `http://localhost:8000/docs`. PostgreSQL starts first; the backend creates its tables and indexes during startup. Database data is stored in a named volume.

## Run Locally Without Docker

### PostgreSQL

Install PostgreSQL 18 for Windows and ensure its service is running. Create the application database once from PowerShell:

```powershell
& "C:\Program Files\PostgreSQL\18\bin\createdb.exe" -U postgres -h 127.0.0.1 tripdeep
```

Copy `.env.example` to `.env` and adjust `POSTGRES_DSN` for your PostgreSQL user, port, or authentication setup. The example connection is:

```text
host=127.0.0.1 port=5432 dbname=tripdeep user=postgres
```

No Docker container is needed for this local setup. The backend automatically creates the application tables and indexes on startup.

### Backend

```powershell
python -m venv backend/.venv
backend/.venv/Scripts/python.exe -m pip install -r backend/requirements.txt
backend/.venv/Scripts/python.exe backend/run_local.py
```

### Frontend

```powershell

```

Vite proxies `/api` to `http://localhost:8000`. Set `VITE_API_BASE_URL` only when the API uses a different origin.

## Core Workflow

1. Enter origin, destination, dates, traveler count, travel mode, stay and food preferences.
2. The orchestrator resolves the destination and runs weather, accommodation, attraction, document, insurance and finance specialists with the trip details.
3. Link uploaded trip documents from **Travel documents**; the document and insurance sections list attachment hints without treating filenames as validated policy coverage.
4. The results are combined into a date-by-date itinerary, forecast-aware clothing suggestions, a document checklist and verified-only finance summary. The Validator remains an internal quality check.
5. Each execution is persisted with request/execution IDs and a validation status. Missing sources and conflicts are recorded rather than silently promoted to verified facts.
6. If execution fails, a sanitized reproduction case is created and appears in **Validation center**. Open it to inspect the input/stack and replay the recorded request.

The initial authentication boundary supports a local development owner only. Production authentication/authorization must be configured before deploying or exposing the service to other users.

## Configuration and Providers

See `.env.example` for database, upload, retry and optional provider settings. Use `DATABASE_BACKEND=memory` only for tests or temporary, non-persistent development. API keys are never sent to the React app or stored in execution records. Leave provider credentials unset when unavailable; the agent will report its actual unavailable state. Booking, payment, cancellation and document-sharing actions require later provider authorization and explicit user confirmation.

Google Weather/Maps, Goibibo, MakeMyTrip, tour providers, insurer documents/knowledge base and an LLM are not connected. Public Open-Meteo and OpenStreetMap endpoints are used for the limited live data described above. To use an LLM, choose and configure a provider first; setting `LLM_PROVIDER=none` leaves the deterministic workflow active.

## Open Specification Decisions

- Airport radius differs across prompts and user examples: 20 km, 30 km and 150 km. It remains configurable; the example's 20 km is used only when explicitly supplied by that trip.
- Room occupancy can mean strict two persons per room in the orchestrator or hotel-specific capacity in the Hotel Agent. The user's explicit trip constraint takes precedence; otherwise provider capacity must be validated.
- Finance example discounts are illustrative; only offers verified against current provider terms can reduce totals.
- Weather has no standalone prompt file. Its initial contract is taken from orchestration prompts and is documented as incomplete.

See [docs/DECISIONS.md](docs/DECISIONS.md) for the current decisions and integration gaps.
