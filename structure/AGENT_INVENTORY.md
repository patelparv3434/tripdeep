# Tripdeep Agent Inventory and Input/Output Matrix

## Source Review

Reviewed all 11 files in `Agent_prompt/`, plus `Documentagent.md` and `promptfordocumetnagent.md`. The two Document-agent files describe the same role at different levels of detail. Weather has no standalone prompt file; its contract is embedded in `ORCHESTRATOR 1.md` and the Travel Planner prompt. The master system orchestrator and Travel Planner Agent overlap and are treated as one orchestration boundary, not two independently counted domain agents.

The 12 agents below are the source-defined agents. Tool/provider access is not assumed to exist just because a prompt names a provider. External results must be marked unavailable until an authorized integration is configured.

## Input/Output Handoff Matrix

| Stage | Agent(s) | Receives | Produces / passes to |
| --- | --- | --- | --- |
| 0: intake | Travel Planner, Validator | User request | Normalized trip request and pre-execution checks |
| 1: feasibility | Travel Planner, Weather | Origin, destination, mode, dates; resolved coordinates | Feasibility and forecast status; stop if impossibility is evidenced |
| 2: logistics (parallel when independent) | Transportation, Hotel, Tour Guide | Trip constraints, party size, dates; Weather for weather-sensitive tours | Sourced inventory, routes, schedules, availability/capacity and costs where verified |
| 3: advice (parallel after required inputs) | Stylist, Document, Health, Dietitian, Insurance | Trip, and relevant Weather/logistics outputs | Structured advisory/document/meal/policy outputs and missing items |
| 4: finance | Finance | Verified costs from transport/hotel/tour/insurance and payment/budget inputs | Reconciled costing, verified offers, payment/cancellation analysis |
| 5: final audit | Validator | Original request and all relevant outputs | Independent cross-check, explicit findings and sign-off/needs review |
| 6: response | Travel Planner | Validated outputs | Consolidated response with source status and user actions |

## Source Conflicts and Missing Specifications

1. **Airport radius:** `ORCHESTRATOR 1.md` sets a 30 km rule; `travelplanneragent 4.md` uses a 150 km example/constraint; the user example says approximately 20 km. Do not silently choose. Keep a configurable threshold, report which source supplied it, and default to the strictest 20 km only for the supplied user example. The system-wide default remains unresolved pending product decision.
2. **Room occupancy:** Orchestrator requires exactly two persons per room and `ceil(total/2)` rooms; the Hotel Agent requires use of provider-specific capacity and can support family rooms/extra beds. Apply the trip's hard two-person rule when explicitly requested; otherwise validate actual hotel occupancy and preserve both values.
3. **Finance offers:** Orchestrator includes specific example discounts; Finance explicitly forbids unverified offers. Treat examples as illustrative only. No discount enters totals without current source, eligibility, terms and validity verification.
4. **Provider access:** Goibibo/MakeMyTrip/Google services are named, but credentials/authorization are absent. Use provider abstractions and explicit `NOT_CONFIGURED`/unavailable responses; do not claim live data or generate synthetic listings as real.
5. **Weather prompt:** No standalone Weather Agent prompt exists. Implement only the output contract embedded in the orchestration prompts and mark the missing independent rules as an assumption.
6. **LLM/provider:** Prompts mention LLaMA/Ollama and, in the Document prompt, GPT-4.1/4o. No API keys or local model setup are supplied. Keep an optional provider interface and deterministic local behavior; no credential requirement for core workflows.
7. **Dietitian required details:** The Dietitian example makes child ages and allergy confirmation gating requirements. These are not supplied in the default trip example, so the agent must return `needs_input`, not a fabricated menu.
8. **Date/examples:** Prompts include multiple trips/dates/destinations, some in the past relative to the stated system date. Examples are test fixtures, not defaults. Reject past dates for new trip execution without altering the prompt examples.

## Evidence and Status Vocabulary

Every non-user-supplied external fact should carry a source and one of: `VERIFIED_LIVE`, `PROVIDER_CONFIRMED`, `CALCULATED`, `ESTIMATED`, `UNVERIFIED`, `UNKNOWN`, or `NOT_CONFIGURED`. Missing information must remain missing. LLM recommendations are not provider evidence.
